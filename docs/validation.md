# schema-4训练、规则与求解验证

日期：2026-09-24。结论：实现和训练／续训链路通过验证，**真实请求完整求解质量尚未达标**。21轮纯相对训练没有获得完整轨迹，独立3份请求的贪心、8次采样和有界搜索也没有完整解。不能据此声称已经具备40勾内求解能力，或保证扩大训练后一定成功。

## 本次实现

- 模型增加股道／机车间全局注意力、明确的取放边界、动作后的有序车列摘要、剩余总预算。默认隐藏维96、3层消息传递，参数345,121。
- 动作概率按股道／类别校正数量选项数，减少候选数量导致的探索偏置。
- 删除失败轨迹的短勾数奖励，单独惩罚循环与死路；完整结果始终优于失败，完整方案按整批总勾数比较。
- 真实轨迹状态池与同状态分支相对学习；前缀回放、保护锚点、配额、历史访问和总勾数持续保留。分支只更新首个新动作。
- 按完整组分配优化器更新块，CPU进程准备环境与候选，GPU合批推理／训练；静态编码与精确决策缓存复用。分支后续推理图不存入训练样本。
- 搜索也支持CPU前沿准备与GPU批量评分，仍使用同一学习权重。
- 终态分配必要条件检查、训练／验证／独立测试日期分区、40勾内完整率及根轨迹／分支独立指标。

没有课程、监督预热、教师、价值头、固定参考模型、自动规则策略接管或旧权重兼容。唯一权重格式为schema 4，计划／事件仍为schema 2。旧schema-3产物已归档到 `runs/archive-v3/`，运行入口拒绝加载。

## 实际训练与续训

硬件：Ryzen 7 3800X，8核16线程，64GB内存；RTX 4080 16GB，PyTorch 2.5.1+cu124。8个CPU环境进程，每进程PyTorch线程数1；GPU BF16，矩阵之外的聚合使用FP32，物理长度仍是整数毫米。

默认训练设置：16组×8条、全局64勾上限、分支组比例0.3、状态池2048、每32条轨迹提交更新、每128个决策图累积梯度、每批2轮更新。64是训练探索上限；完整率另统计总勾数≤40。

先训练8轮，再续训12轮，最后从20轮检查点续训1轮到默认输出路径。累计：

真实检查点重载确认迭代连续、池覆盖所有68个训练请求、训练与验证不重叠。最终14份日期留出验证：贪心0／14；每份8次采样中至少一次完成的请求数0／14。

21轮采样与更新累计约609.5秒，加权吞吐约240.5个新增环境动作／秒；逐轮199.6—288.3。最后一轮6,584动作、采样18.94秒、更新7.34秒、合计26.31秒，约250.2动作／秒。这里不含进程启动、定期验证和落盘。最后一次续训的PyTorch峰值分配约804MiB，不是整张GPU的全部显存使用量。

以上是短程功能验证中的实测，不是严格消融实验。旧schema-3网络、预算与采样构成不同，旧吞吐不能直接作为新版加速比。模型表达更丰富会增加计算；缓存命中、分支比例或组内得分改善都不能单独证明单位时间更容易得到完整解。

## 后续验收边界

这次完成了模型、相对学习、并行与验证实现，尚未证明新增机制提升完整率。扩大训练应持续观察验证完整率、首次完整解所需环境步数、成功总勾数及循环率；不能以采样量大或局部得分上涨判定策略可靠。

道岔组合、折返清尾、连续跨区段占用及机／调合并临停空间仍缺现场参数。当前规则证明的是抽象物理与已确认业务条件；一次临停合法不证明之后一定拿得出或全局可恢复。训练与批量搜索没有取消这些边界。
